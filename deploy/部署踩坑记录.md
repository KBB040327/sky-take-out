## 🕳️ 踩坑清单（面试重点）

### 坑 1：openEuler 自带源里的 Docker 是 2018 年的版本

**现象**
```
$ dnf list --available | grep docker
docker-engine.x86_64    2:18.09.0-357.oe2403sp1    update
docker-compose.noarch   1.22.0-4.oe2403sp1         everything
```
Docker 18.09 + Compose v1（`docker-compose`，Python 写的那个）

**问题**：现在的教程和公司都用 `docker compose`（v2 插件语法），v1 和 v2 的用法有差异

**解决**：改用 Docker 官方 CE 源
```bash
rpm --import https://mirrors.aliyun.com/docker-ce/linux/centos/gpg
# 写 /etc/yum.repos.d/docker-ce.repo，baseurl 指向 aliyun 镜像
```

**结果**：装到 Docker **26.1.3** + Compose **v2.27.0**

---

### 坑 2：openEuler 的 `$releasever` 和 EL8 源路径不匹配

**现象**：Docker CE 的源地址是
```
https://mirrors.aliyun.com/docker-ce/linux/centos/$releasever/$basearch/stable
```
但 openEuler 上 `$releasever` 会解析成 **`24.03`**，这个路径不存在 → 404

**排查**
```bash
rpm -E '%{rhel}'     # 输出 %{rhel}（字面量），说明 openEuler 不认这个宏
cat /etc/os-release   # VERSION_ID="24.03"
```

**解决**：在 repo 文件里**把 `$releasever` 硬编码成 `8`**（openEuler 与 EL8 的包格式兼容）

---

### 坑 3：`container-selinux` 依赖卡住安装

**现象**：`dnf install docker-ce` 报依赖不满足

**解决**
```bash
dnf install -y --setopt=install_weak_deps=False docker-ce docker-ce-cli \
    containerd.io docker-buildx-plugin docker-compose-plugin
```
`install_weak_deps=False` 跳过弱依赖（openEuler 自带源里有 `container-selinux`，会被自动装上）

---

### 坑 4：用 JDK 8 打包失败 —— `无效的标记: --release`

**现象**
```
[ERROR] Failed to execute goal maven-compiler-plugin:3.10.1:compile:
        Fatal error compiling: 无效的标记: --release
```

**排查**
```bash
grep java.version pom.xml    # → 17
java -version                # → 1.8（我把 JAVA_HOME 切到了 JDK 8）
```

**原因**：`--release` 是 **JDK 9+ 才有**的编译参数，JDK 8 的 javac 不认识

**教训**：**打包前先看 pom 里的 java.version**，别凭"这是个老项目"就想当然

**解决**：用 **JDK 17** 打包（项目本来就是 Java 17 + SpringBoot 2.7.3）

### 坑 5：容器之间不能用 `localhost` ⭐ 最经典

**现象**：应用起来了，但连不上数据库

**原因**
- `application-dev.yml` 里写的是 `host: localhost`
- 但在容器里，**`localhost` 指的是容器自己**，不是 MySQL 容器

**解决**：用 Docker Compose 的**服务名**互访
```java
// 错误：jdbc:mysql://localhost:3306/sky_take_out
// 正确：jdbc:mysql://mysql:3306/sky_take_out      ← mysql 是 compose 里的服务名
```

**关键技巧（不用改代码）**：Spring Boot 里**环境变量的优先级高于 application.yml**，
所以直接在 compose 里覆盖就行：
```yaml
environment:
  SKY_DATASOURCE_HOST: mysql      # 覆盖 sky.datasource.host
  SKY_REDIS_HOST: redis           # 覆盖 sky.redis.host
```

> Spring Boot 的**宽松绑定**会把 `SKY_DATASOURCE_HOST` 映射到 `sky.datasource.host`。
> 这样同一份 jar 在本地（localhost）和容器里（服务名）都能跑。

### 坑 6：数据库里存的是明文密码，代码却用 MD5 比对

**现象**
```bash
$ curl -X POST /admin/employee/login -d '{"username":"admin","password":"123456"}'
{"code":0,"msg":"密码错误"}
```

**排查**
```sql
SELECT username, password FROM employee;
-- admin | 123456      ← 存的是明文！
```
```java
// EmployeeServiceImpl
password = DigestUtils.md5DigestAsHex(password.getBytes());   // 输入被 MD5 了
```

**原因**：**输入的密码被 MD5 后再比对，但库里存的是明文** → 永远不可能相等

**解决**
```sql
UPDATE employee SET password = MD5('123456') WHERE username='admin';
-- 得到 e10adc3949ba59abbe56e057f20f883e
```

**结果**：登录成功，返回 JWT token

### 坑 7：`/admin/shop/status` 首次调用 500

**现象**
```
java.lang.NullPointerException:
  Cannot invoke "java.lang.Integer.intValue()" because "status" is null
    at com.sky.controller.admin.ShopController.getStatus(ShopController.java:44)
```

**原因**：店铺营业状态存在 Redis 里，**但从来没写过** → 读出来是 `null` → 拆箱成 `int` 时报 NPE

**解决**：先调用一次写接口初始化
```bash
curl -X PUT /admin/shop/1 -H "token: $TOKEN"   # 1=营业中
curl     /admin/shop/status -H "token: $TOKEN" # → {"code":1,"data":1}
```

**教训**：**依赖外部状态的接口，要有初始化逻辑或默认值**，否则首次调用必崩

### 坑 8：Nginx 反代 WebSocket 必须加两个头

**现象**：来单提醒不工作，浏览器控制台报 WebSocket 握手失败

**原因**：Nginx 默认用 HTTP/1.0 转发，且不传递 `Upgrade` 头

**解决**
```nginx
location /ws/ {
    proxy_pass http://app:8080/ws/;
    proxy_http_version 1.1;                        # ← 必须
    proxy_set_header Upgrade    $http_upgrade;     # ← 必须
    proxy_set_header Connection "upgrade";         # ← 必须
    proxy_read_timeout 3600s;                      # 长连接别被掐断
}
```

### 坑 9：内存受限必须限制 JVM 堆

虚拟机只有 **3.3G 内存**，如果 JVM 用默认堆（通常是物理内存的 1/4，约 800M+），
再加上 MySQL、Redis、Nginx，很容易触发 **OOM Killer**（容器被系统杀掉，且没有明显报错）。

**解决**

| 组件 | 限制方式 | 值 |
|---|---|---|
| app | `-Xmx` | 384m |
| app | `-XX:MaxMetaspaceSize` | 128m |
| mysql | `--innodb-buffer-pool-size` | 192M |
| mysql | `--performance-schema=OFF` | 省 100M+ |
| redis | `--maxmemory` | 96mb |
| redis | `--maxmemory-policy` | allkeys-lru |
